# Как запустить Roadwatch без своего компьютера: исследование вариантов

Проверено **12 ноября 2026 года**. Задача: Москва и область, 50–100 камер, возможные ДТП/дым/огонь, самостоятельная работа при закрытом браузере, журнал и фрагменты видео, бюджет пользователя 0 ₽.

**Обновление 13 ноября:** пользователь исключил любую привязку карты. Ниже сохранён сравнительный обзор, а актуальное решение — [NO_CARD_PLAN.md](NO_CARD_PLAN.md). Oracle и Modal исключены; Northflank не включён из-за противоречивых требований payment method. Гранты и иные сервисы не считаются подходящими до проверки no-card условий.

Это широкий обзор практически применимых классов решений, а не обещание проверить каждый хостинг интернета. Документация, тарифная страница, доступность регистрации, полученная машина и измеренная производительность — разные уровни подтверждения. Ни одного внешнего аккаунта, платного ресурса или грантовой заявки в ходе исследования не создавали. Реальных источников по-прежнему **0**.

## Вывод и порядок выбора

1. **Небольшой бесплатный пилот:** проверить Northflank Sandbox и Oracle A1, если пользователь имеет право зарегистрироваться и ресурс фактически доступен. Начать с одной камеры; число 5–10 — ступени тестирования, не обещанная вместимость.
2. **50–100 камер с видео до события:** наиболее реалистичен выделенный облачный ресурс по гранту либо серверная интеграция с владельцем камер. Бесплатность здесь обеспечивает стороннее финансирование, а не отсутствие расхода ресурсов.
3. **Большой охват с ограниченным CV:** snapshots от оператора + его архив + обработка по расписанию/по подозрению. Возможность зависит от API источника. Такой режим подходит прежде всего для устойчивых признаков дыма и последствий происшествия; качество распознавания момента столкновения надо проверять отдельно.
4. **Бесплатные GPU:** использовать для обучения, проверки моделей и редких дополнительных проверок; общедоступные бесплатные квоты не подтверждают непрерывную обработку всех потоков.

Сначала получить один разрешённый пригодный поток и ресурс без платного перерасхода. Затем измерить полный тракт, включая decode, сеть, память и запись. Наличие одного только сайта или модели эту проверку не заменяет.

## Что изменилось относительно исходного плана

- У Vercel есть **Daemons**, включая Hobby. Поэтому общее утверждение «Vercel вообще не умеет постоянные процессы» неверно. Однако отдельные квоты Daemons не обеспечивают полный месяц непрерывной работы минимального экземпляра; подробности ниже.
- Northflank Sandbox — дополнительный кандидат для постоянного экспериментального процесса. Между pricing и billing docs есть противоречие о банковской карте; квоты доступного аккаунта ещё не проверены.
- Cloud.ru закрывает создание бесплатной VM аккаунтам, зарегистрированным после 30 июня 2026 года. Новый пользователь не должен планировать эту старую акцию.
- Документация Yandex Cloud, обновлённая 3 ноября, сообщает о недоступности обычного trial/стартового гранта новым клиентам. Некоторые рекламные страницы продолжают упоминать 4000 ₽: считать их гарантированным предложением нельзя. Cloud Boost — отдельная программа.
- У Hugging Face различаются обычные CPU/Docker Spaces и специальная программа ZeroGPU. Их условия нельзя смешивать.

## Наиболее интересные новые кандидаты

### Northflank: постоянный экспериментальный collector

[Pricing](https://northflank.com/pricing) обещает no sleeping, два сервиса и до $20 ресурсов ежемесячно. Но [billing docs](https://northflank.com/docs/v1/application/billing/pricing-on-northflank) требуют payment method для всех аккаунтов и не рекомендуют Sandbox для production. Не обещаем регистрацию без карты или production SLA до проверки.

Оценка по публичным ставкам, **не гарантированная конфигурация Sandbox**: 0.5 vCPU + 1 GB на 720 часов стоят около $12 до диска, сети и других ресурсов. Egress $0.06/GB существенно меняет итог, если непрерывно отправлять кадры внешней модели. BYOC 12 vCPU/48 GB означает управление чужим облаком; железо этого облака Northflank бесплатно не выдаёт.

Проверить: доступный план/регион, квоты CPU/RAM, network policy, persistent volume, остановку при исчерпании free allowance. Наш SQLite API требует persistent volume; переход на managed Postgres потребует изменения кода.

### Oracle: наиболее прямой путь к своей облачной VM

В текущих [официальных лимитах](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm) A1 соответствует 2 OCPU/12 GB, а не популярным старым 4/24. Исходящий allowance — 10 TB/месяц. Доступность формы регистрации, региона, конкретной shape и ресурсов для этого пользователя не подтверждена.

На VM можно держать API, FFmpeg и небольшой detector, если полный замер помещается в CPU/RAM. ARM-совместимость моделей/библиотек проверяется на самой машине. Бесплатная VM без гарантии выдачи/сохранения не равна гарантированному 24/7.

### Modal: дополнительная модель по подозрению

[Starter pricing](https://modal.com/pricing) включает $30/месяц; T4 — $0.000164/сек, CPU и RAM оплачиваются отдельно. Функция может работать до [24 часов](https://modal.com/docs/guide/timeouts), что само по себе не даёт бесплатную непрерывную GPU.

Наш расчёт: даже если отдать T4 все $30, получится максимум около 50.8 GPU-часа до CPU/RAM. При резерве $20 и условных 0.125 CPU + 0.5 GiB — около 33.3 часа; фактическая модель может требовать больше. Для 100 камер × 0.2 fps это 51.84 млн кадров/месяц: нужно около 432 кадров/сек в доступные 33.3 часа, включая фактический runtime. Такая производительность не измерена. Значит, выгоднее отправлять небольшую долю кандидатов.

У [budgets](https://modal.com/docs/guide/budgets) различаются cap на usage до кредитов и spend limit после кредитов. Проверить допустимость нулевого spend limit и оставлять запас; кредиты аккаунта могут расходоваться другими задачами. Интеграция пока не реализована.

### Vercel: обновлённая оценка

[Daemons](https://vercel.com/docs/daemons) действительно поддерживают постоянный container process. У Hobby в [специальных лимитах](https://vercel.com/docs/daemons/limits) — 5 CPU-ч и 420 GB-ч/месяц, минимум 1 GiB. В расчётных единицах документации 420 / 1 = 420 часов, около 17.5 суток, даже без CPU-работы. Default 2 GiB исчерпает память быстрее. Persistent local storage и inbound HTTP/TCP у Daemons не поддерживаются. После исчерпания квоты процессы останавливаются.

Поэтому Vercel подходит для интерфейса и небольших обработчиков, но найденная новая функция не закрывает наш полный месячный видеопайплайн за $0. Не переносить численные лимиты Functions на Daemons: это разные таблицы.

### Hugging Face: специальное исключение ZeroGPU

[Общие Spaces docs](https://huggingface.co/docs/hub/en/spaces-overview) требуют платный план для нового CPU Basic compute Space. [ZeroGPU docs](https://huggingface.co/docs/hub/spaces-zerogpu) отдельно разрешают до двух ZeroGPU Spaces бесплатному аккаунту с подтверждённой почтой и возрастом более 30 дней. У Free visitor — 5 GPU-минут/день, очередь; Gradio-совместимость обязательна. Это специальное предложение, которое нужно проверить в интерфейсе аккаунта, а не основание обещать обычный бесплатный Docker worker.

## Шесть схем пайплайна

| Схема | Что работает постоянно | Можно получить видео до события? | Главный компромисс |
|---|---|---|---|
| A. Облачная VM + continuous streamcopy | Приём каждого потока, ring buffer, decode и CV | Да, из своего буфера при непрерывном приёме | Постоянная сеть и decode; нужны ресурсы |
| B. Подпоток + основной поток | Малый поток для CV; основной для архива или по запросу | Основное качество — только если основной поток уже буферизуется/доступен архив | Запуск основного после тревоги не восстанавливает прошлое |
| C. Snapshot API + архив оператора | Опрос свежих JPEG, lightweight CV | Да, если документированный архив реально предоставляет нужный интервал | Зависимость от API/срока архива и точности часов |
| D. Snapshot API без архива | Опрос JPEG | Нет; только снимки и последующая запись | Не удовлетворяет обязательному pre-roll |
| E. Метаданные/события от оператора | Наша подписка на webhook/API | Если событие включает разрешённый clip URL/API | Нужен партнёр; модель может быть чужой |
| F. Сервер партнёра рядом с камерами | Буфер/CV у владельца, нам события и клипы | Да, при реализации у партнёра | Бесплатность для пользователя зависит от соглашения |

**Рекомендуемый стек для A:** текущий API + persistent SQLite + FFmpeg/MediaMTX + CPU detector; интерфейс на уже опубликованном статическом хостинге. [MediaMTX](https://github.com/bluenviron/mediamtx) даёт транспорт live/record/playback, а не детектор ДТП. Его [запись](https://mediamtx.org/docs/features/record), [playback](https://mediamtx.org/docs/features/playback) и [auth](https://mediamtx.org/docs/features/authentication) помогают закрыть отсутствующий live gateway. Он ещё не добавлен в проект.

**Для C:** камера → snapshot API → detector → event → запрос t−20…t+10 к архиву → приватный clip → журнал. Проверить, что snapshot и архив относятся к одной камере/временной шкале. Обычный live HLS может иметь короткое скользящее окно; наличие m3u8 не означает полноценный архив. Семантика playlist/удаления сегментов описана в [RFC 8216](https://www.rfc-editor.org/rfc/rfc8216).

Браузерный WebGPU технически возможен через [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html), но использует компьютер посетителя и не работает как наш независимый recorder при закрытой вкладке. Поэтому как основу этого проекта его исключаем. Добровольные серверы могут дать ресурсы только по явному соглашению; непрерывность, доверие и контроль данных остаются задачами.

## Как экономить без подмены требований

1. **Буферизовать сжатый поток без перекодирования.** [FFmpeg streamcopy](https://www.ffmpeg.org/ffmpeg.html) копирует пакеты без decode/encode, но ветка inference всё равно должна декодировать кадры. Фильтр fps после decode не доказывает уменьшение стоимости декодирования исходного 25 fps потока.
2. **Брать готовый малый подпоток или JPEG у источника.** У [Frigate](https://docs.frigate.video/configuration/cameras/) роли detect и record разделены. Создание уменьшенной копии самим сервером всё равно требует decode; запрос уже уменьшенного потока у камеры меняет нагрузку раньше.
3. **Один приём на камеру, несколько потребителей.** Не открывать независимые upstream connections для каждой карточки пользователя. В live отдавать только выбранную камеру; фиксировать frame timestamps для совпадения рамок.
4. **Проверять область дороги и временную устойчивость.** Background/motion gate полезен только как кандидат; постоянный транспорт, тени и дождь делают его шумным. Малый начальный огонь или дым могут не пройти такой gate. Recall каскада измерять на полном потоке, а не только на допущенных кадрах.
5. **Разделить задачи.** Дым/огонь: компактный detector и temporal checks; столкновение: траектории + temporal модель/правила; тяжёлая проверка только на коротких кандидатах. По редким JPEG уверенно восстановить удар нельзя.
6. **INT8, batching, ограничение потоков.** [ONNX Runtime](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html) предлагает квантование, но скорость и потерю качества нужно измерять. Для GPU есть [DeepStream batching](https://docs.nvidia.com/deepstream/text/DS_plugin_gst-nvstreammux2); без предоставленного GPU он ресурсов не создаёт.
7. **Хранить события и агрегаты.** При 100 × 0.2 fps возникает 1.728 млн наблюдений/день. Писать каждое в D1 с allowance 100 тыс. rows/day нельзя. Нужны локальные результаты и агрегация; индексы/удаления тоже расходуют write allowance. Текущий API хранит каждое наблюдение: перенос в D1 требует изменения дизайна.

## Арифметика, которую легко упустить

Допущения ниже не являются benchmark или подтверждённой квотой камеры. Месяц = 30 суток, GB десятичные.

| Режим на 100 камерах | Входящий трафик/сутки | Только inference при 50 мс CPU/кадр | Ограничение |
|---|---:|---:|---|
| 1 Mbps video, inference 1 fps | 1080 GB | 3600 CPU-ч/мес. | Не включает decode |
| Тот же video, inference 0.2 fps | 1080 GB | 720 CPU-ч/мес. | Снижение FPS не снижает входящий bitrate |
| Настоящий substream 0.25 Mbps, 0.2 fps | 270 GB | 720 CPU-ч/мес. | CPU модели не изменится, если input тот же |
| Настоящий JPEG API, 50 KB каждые 5 секунд | 86.4 GB | 720 CPU-ч/мес. | Нет непрерывного локального видео и гарантии момента удара |
| JPEG 50 KB каждые 30 секунд | 14.4 GB | 120 CPU-ч/мес. | Текущий 6-секундный temporal gate с таким шагом несовместим |

**50 мс — не физический нижний предел.** При 100 камерах × 0.2 fps модель с измеренными 5/15/50 мс суммарного CPU-времени потребовала бы соответственно 72/216/720 CPU-ч в месяц. Поэтому одних расчётов с 50 мс недостаточно, чтобы доказать невозможность любого бесплатного варианта. Но малый input/ускорение могут ухудшать обнаружение дальнего дыма и автомобилей; суммарное CPU-время нельзя заменять wall time многопоточного inference. Дополнительные модели и подготовка изображения также считаются.

Наиболее интересная **непроверенная гипотеза для 100 точек**: готовые JPEG каждые 5 секунд + быстрый CPU detector на предоставленной free VM + доступный архив оператора для pre/post записи. Для её подтверждения одновременно нужны право и квота на частый опрос 100 разных точек, свежие снимки, достаточное качество на таком шаге, измеренный CPU/RAM, бесплатный сетевой бюджет и достаточно длинное окно архива с точным временем. Это может оказаться реализуемым для устойчивых признаков дыма/огня или последствий ДТП; обещать детекцию самого столкновения на такой частоте нельзя. Ни один из этих внешних наборов условий пока не подтверждён.

Отправка всех JPEG из предпоследней строки внешнему inference превращает их в **2592 GB исходящего трафика в месяц** у collector. При ставке Northflank $0.06/GB это около $155.52 только на egress до каких-либо включённых льгот. Поэтому «бесплатный GPU API» не делает бесплатным перенос всех кадров к нему. Обработка рядом с приёмом либо отбор редких кандидатов важнее числа провайдеров.

100 событий/день × 30 секунд × 1 Mbps × 7 дней ≈ 2.625 GB архива. 1000 событий/день — 26.25 GB. Ложные тревоги определяют цену хранения; нужен байтовый cap, retention и приватные ссылки. Сам ring buffer на 60 секунд — около 0.75 GB для 100 потоков по 1 Mbps, но сеть должна непрерывно его наполнять.

| [MosDay](https://mosday.ru/webcam/list.php?type=extended) | Список существует, но помечен как **архив** | Записи каталога не доказывают нынешнюю работоспособность | Только поиск владельца, не импорт «100 активных» |
| [GEOCAM Москва](https://www.geocam.ru/in/moscow/) | Каталог содержит описания дорожных ракурсов | Не подтверждены свежесть, права на continuous access и 100 разных точек | Вторичный discovery, проверка у первоисточника |

Здесь не установлен факт отсутствия камер вообще. Установлено отсутствие **проверенного доступного нам набора** 50–100 разрешённых потоков с нужной географией. Адрес установки, CCTV-реестр, player embed и доступная запись — разные вещи. Не подменять точки одного кольца камерами из другого города или несколькими ссылками на один upstream.

Нужно зафиксировать для каждой камеры: владелец и канал доступа, фактическое направление/ROI дороги, координаты с источником, разрешённые способы обработки и хранения, HTTPS/HLS/RTSP параметры, freshness, архив, substream, rate limit, расписание и стабильность. В конфигурацию включать только после проверки свежего кадра и условий.

## Модели: что брать за основу

| Компонент | Кандидаты / исследование | Решение |
|---|---|---|
| Дорожный detector | [RF-DETR](https://github.com/roboflow/rf-detr), компактные ONNX-модели | Сравнить CPU latency/recall дальних объектов; RF-DETR имеет разные лицензии по вариантам, проверять конкретный checkpoint |
| Траектории | [ByteTrack](https://github.com/FoundationVision/ByteTrack) | Детектор + tracker помогают найти кандидата; сами не доказывают столкновение |
| ДТП | [kircova/Car-Crash-Detection](https://github.com/kircova/Car-Crash-Detection) | Репозиторий использует YOLOv3 и аномалии скорости/угла/пересечения; исследовательский baseline, не готовая гарантия на 100 московских камерах |
| CCTV dataset ДТП | [ACCIDENT](https://accidentbench.github.io/index.html) | Ближе к фиксированным камерам, чем dashcam; проверить лицензию и делать независимый тест на московских сценах |
| Дым/огонь | [D-Fire](https://github.com/gaia-solutions-on-demand/DFireDataset) | Кандидат для обучения; отдельно добавить сложные отрицательные сцены и временную проверку |
| 3D Gaussian segmentation | [kircova/Semantic-Seg-Gaussian-Splats](https://github.com/kircova/Semantic-Seg-Gaussian-Splats) | CUDA/DINO/Gaussian training pipeline; для первого 2D road-event MVP не нужен |

Существующий collector принимает определённый YOLOv8 ONNX layout. RF-DETR, temporal classifiers и tracker нельзя подключить простой сменой имени весов: нужны свои адаптеры и контракт результатов.

У Ultralytics есть [AGPL/Enterprise условия](https://www.ultralytics.com/license). Формат ONNX не отменяет условия происхождения весов. Приватный репозиторий сам по себе не решает вопрос лицензирования сетевого приложения; конкретные условия моделей проверять до выбора. Ни один checkpoint в ходе исследования не признан production-ready и не установлен.

## Уведомления и закрытая вкладка

Источником истины остаётся серверная БД. Отдельный outbox после commit события отправляет уведомление и повторяет попытки с дедупликацией. Два варианта: [Web Push](https://developer.mozilla.org/en-US/docs/Web/API/Push_API) с подпиской/разрешением пользователя или [Telegram Bot API](https://core.telegram.org/bots/api) с заранее подключённым пользователем. Бесплатные сообщения имеют [лимиты](https://core.telegram.org/bots/faq); платный broadcast для пилота не включать. Доставку на устройство в любой момент гарантировать нельзя.

При возвращении на сайт журнал загружается из БД, независимо от успешности push. В уведомлении ссылка на приватное событие, не вечный публичный URL видео. Текущая v0.1 имеет журнал, но не outbox/Web Push/Telegram sender. Никому сообщений в рамках исследования не отправляли.

## Конкретный план проверки

| Шаг | Что проверяем | Условие продолжения |
|---|---|---|
| 1 | Один источник у владельца | Свежие кадры, география, право cloud CV/записи, допустимая частота |
| 2 | Northflank/Oracle или выданный грант | Реальная квота, persistent storage, региональный доступ, остановка до платного расхода |
| 3 | 1 камера, 24 часа | Свежесть, reconnect, CPU/RSS/decode/сеть/disk, пропуски и клип pre/post |
| 4 | 5, затем 10 камер по 72 часа | Есть запас на рестарт/пики, запись не опаздывает, cost ledger сходится с provider metrics |
| 5 | Размеченные эпизоды и отрицательные часы | Event recall, false alarms/camera/day, задержка p50/p95, доля клипов с полным pre-roll |
| 6 | 50/100 только по прогнозу из замеров | CPU/RAM/egress/IO/лимиты источника в квотах; если нет — снижать масштаб либо получать грант |

Не задаём выдуманный обязательный accuracy для ещё не выбранных камер. До пилота согласовать приемлемые recall/false alarms/latency и оценивать доверительные интервалы на достаточном числе размеченных событий. Accuracy по картинкам не заменяет event metrics.

## Что потребуется от внешних сторон

- Пользовательский cloud account с допустимой регистрацией и фактическими free resources; регистрация/проверка личности не выполнены агентом. Публичная документация не подтверждает доступность зарубежного аккаунта пользователю из РФ.
- Для гранта — соответствующий статус, заявка, одобрение, допустимые продукты и дата окончания. Не закладывать все рекламные «до миллиона» как автоматически доступные деньги. У Timeweb и Cloud.ru есть явные исключения GPU.
- От владельца видео — пригодные источники/архив и условия их использования. Публичный просмотр не подтверждает разрешение на непрерывную машинную запись или ретрансляцию.

На сегодня приоритет: **источник → доступный постоянный compute → один реальный тракт → измерения → грант/масштабирование**. Гарантированное бессрочное 24/7 для 100 камер за 0 ₽ по найденным общедоступным условиям не подтверждено.
