# Пропуски транспорта и задержка: исправление 14 ноября 2026

## Что обнаружено

Фактический Hostrix всё ещё передавал одиночные кадры старого профиля 5 fps. Сервер обрабатывал больше кадров, чем успевал отправлять отдельными HTTP-запросами. Короткие детекции могли не попасть на экран. Предыдущее исправление сайта устранило пустой экран, но не заменило код коллектора на аккаунте владельца.

FFmpeg также оставлял JPEG quality автоматическим. В сравнительном образце медиана файла оказалась 5768 байт при исходном разрешении 480×270; при явном q=3 — 25669 байт. Это дополнительная потеря мелких деталей перед детектором. Низкое исходное разрешение и задержка HLS остаются свойствами источника.

OpenCV выполнялся прямо в asyncio loop: на слабом CPU это задерживало HTTP/leases/heartbeat. Теперь анализ идёт через asyncio.to_thread под тем же единственным inference lock; вычислительный бюджет и gates сохраняются.

## Что изменено

- Hostrix — 4 fps; JPEG q=3 без upscale. Новых зависимостей и весов нет.
- Детектор возвращает candidates от score 0.18. Новый ID создаётся только от 0.25. Более слабая рамка может восстановить существующий ID при геометрическом совпадении, но сама объект не создаёт. Высокие scores сопоставляются первыми. Подход использует идею low-score association из [ByteTrack](https://arxiv.org/abs/2110.06864), но это собственный небольшой LK-трекер, не реализация полного ByteTrack.
- Пересекающиеся vehicle-рамки разных классов дополнительно подавляются NMS. Для optical flow — до 20 углов, qualityLevel 0.01, minDistance 2, прежняя проверка вперёд/назад. Если движения измерить нельзя, рамка не рисуется. Потерянная позиция хранится до 1.5 с только для восстановления ID следующей настоящей детекцией.
- Worker сохраняет окно до 12 реальных кадров / 3 секунд. Оно объединяет соседние пакеты, поэтому опрос браузера не теряет весь промежуточный пакет. Лимит JSON 800 КБ; квота учитывает только новые кадры, повтор запроса не оплачивается дважды.
- Браузер опрашивает через 200 мс после ответа, воспроизводит исходные временные метки с 250 мс буфером джиттера. При старте отбрасывает накопление старше 1750 мс от последнего кадра (до восьми кадров при 4 fps). Это не генерация промежуточных картинок или координат.

## Измеренное сравнение одной записи

Публичная CBTV51: 14.11.2026, 08:27:53–08:28:18 CT, 25 секунд, 100 кадров при 4 fps, detector interval 0.65 с. Настоящие закреплённые ONNX-веса. [Машиночитаемый результат и хеш образца](tracking-comparison.json).

| Профиль | Кадров хотя бы с одним треком | Всего наблюдений треков | Из них optical flow |
| --- | ---: | ---: | ---: |
| Предыдущий | 20 / 100 | 27 | 11 |
| Только JPEG q=3 | 23 / 100 | 29 | 7 |
| JPEG + новые правила трекера | 58 / 100 | 115 | 68 |

Это **не recall 58% и не доказательство распознавания всех машин**: полной ручной разметки и измерения false positives нет. Большее число ID также не доказывает лучшую устойчивость идентичности. На коротком образце получено больше кадров с выданными треками, но качество нужно оценивать отдельно. CPU сравнения измерен на Darwin arm64 для регрессии, а не как ресурс Hostrix; допуск облачного исполнения проверяется отдельно в Linux 0.5 CPU / 512 МиБ.

Воспроизведение с собственным сохранённым образцом:

```sh
python tools/compare-tracking.py --video sample.mp4 --model vehicles.onnx \
  --baseline-ref c7351b8 --output comparison.json
```

## Развёртывание и честные пределы

Фронт/API публикуются отдельно. Новый трекер, JPEG и неблокирующий collector включатся после Upload/Unzip свежего roadwatch-hostrix-fix.zip на Hostrix. Не использовать Redeploy; существующие пакеты, модели и secrets сохраняются. Команда прежняя, ROADWATCH_MODE=run.

На бесплатном 0.5 CPU цель — 4 fps, не плавность 25–30 fps. Отдельная квота 24000 кадров просмотра в сутки даёт примерно 100 минут просмотра при полных 4 fps; фоновые fire/smoke, трекинг и обработка событий продолжаются независимо от вкладки. Ни это исправление, ни скриншоты не подтверждают accuracy ДТП или безотказность 24/7.

Скриншоты README сняты с реального опубликованного фронта и работающего Hostrix. Они подтверждают наличие изображения и согласованных рамок в этот момент, а не полноту детектора или применение нового пакета на сервере.
