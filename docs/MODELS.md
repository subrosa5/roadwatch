# Детекторы и оценка качества

## Что реализовано

Collector умеет загрузить локальный ONNX-экспорт YOLOv8 object detection с выходом `[1,4+C,N]` или `[1,N,4+C]`, применить letterbox, проверить размерность labels, выполнить inference OpenCV DNN на CPU и per-class NMS. Весовой файл сверяется с SHA-256 из манифеста. Несовместимый layout приводит к отказу, а не к случайной интерпретации рамок.

Нет обученных и проверенных в этом проекте моделей для ДТП, дыма и огня. Демо использует программно созданные видео и заранее заданные рамки. Изображение автомобиля с прямоугольником не доказывает работу детектора аварий.

## Требуемые модели

- Object detector транспорта: `vehicle`. Сам по себе не определяет ДТП.
- Smoke/fire detector: модели/классы `smoke` и `fire`, обученные и оценённые на подходящих сценах.
- Collision detector или temporal-модель: `collision`. Нельзя переименовать обычный класс «car» в «collision» и считать задачу решённой.

Текущий адаптер не поддерживает segmentation/pose/transformer output, трекинг и модели на последовательностях видео. Для temporal-классификатора нужен новый adapter с сохранением времени/последовательности и отдельной проверкой latency.

## Манифест модели

```json
{
  "path": "/models/fire-smoke.onnx",
  "sha256": "REAL_64_HEX_SHA256",
  "labels": ["smoke", "fire"],
  "size": 640,
  "threshold": 0.5
}
```

Путь и hash — placeholders. Дополнительно в карточке модели фиксировать источник весов, commit/release, лицензию, class order, preprocessing, dataset/split, используемую версию OpenCV и известные ограничения. Автоматический download непроверенных весов отключён. Лицензии модели и датасета анализируются отдельно от собственного кода проекта.

## До подключения к реальным тревогам

1. Собрать разрешённые примеры нужного ракурса и освещения. Не обучаться и не оцениваться на соседних кадрах одного эпизода в разных splits.
2. Разделить train/validation/test по камерам/датам/событиям, чтобы близкие кадры не создавали утечку.
3. Зафиксировать baseline без модели и baseline детектора; параметры выбирать на validation, не на test.
4. Проверить сложные отрицательные случаи: пробки, буксировка, остановившаяся машина без ДТП, туман, выхлоп, пар, солнце/фары, сварка, блики, снег, дождь, грязный объектив, низкий bitrate и резкая смена PTZ.
5. Отдельно оценить ночь/день, дальние/маленькие объекты, камеры разных типов и потерю кадров.
6. Опубликовать event-level precision/recall, ложные тревоги на camera-hour, задержку обнаружения от размеченного начала, долю времени без наблюдения и полноту видеофрагмента.

mAP детектора и самооценка VLM не заменяют event-level метрики. Два положительных кадра уменьшают некоторые случайные срабатывания, но не обеспечивают независимость ошибок модели.

## Ресурсный benchmark

Облачный тест 1 → 5 → 10 потоков с одинаковыми разрешением/FPS/model hashes. Измерять отдельно:

- Приём: доступность, реальный bitrate, количество разрывов, время reconnect.
- Decode: суммарный CPU FFmpeg, RSS, число процессов, disk IO.
- Inference: CPU time, p50/p95 wall latency, RSS и threads.
- API/storage: request rate, WAL/checkpoint overhead, disk growth.
- Evidence: время post-roll + сборки, codec совместимость, размер и наличие pre-roll.
- Клиент: свежесть показанного кадра, совпадение frame_id, скорость открытия клипа.

Только после этого допускается экстраполяция на 50–100 камер с резервом. Текущая гипотеза 50 мс/кадр — арифметический параметр калькулятора, не результат модели.
