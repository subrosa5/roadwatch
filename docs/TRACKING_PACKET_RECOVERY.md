# Восстановление доставки после задержки пакета

После запуска v3 API подтвердил работающий collector и реальные vehicle ID, но проверка длительного просмотра обнаружила паузы. Worker-логи содержали POST /tracking с HTTP 400. Сам код ответа не раскрывает конкретную причину остановки процесса на Hostrix; для неё нужен его свежий лог либо типизированная серверная диагностика.

Воспроизведён отдельный дефект протокола: пакет с кадром шестисекундной давности и свежим последним кадром целиком отклонялся из-за ограничения длительности пакета. Клиент мог рассматривать такое отклонение как постоянную ошибку и завершать процесс. Раньше regression test получал 400 вместо ожидаемого 200.

Теперь API сначала проверяет согласованность всех пар JPEG/annotation, роли, хеши и порядок кадров. Последний кадр по-прежнему обязан быть моложе пяти секунд. После этого старая часть пакета отбрасывается, а свежая принимается. В квоту входят только оставшиеся новые кадры. Протухший целиком пакет, неверный хеш или неверные рамки остаются отклонёнными.

Добавлены фиксированные коды диагностических сообщений tracking_ingest. В них нет текста запросов, изображений, ключей, подписанных URL или произвольного содержимого ошибок. Это позволит отличать frame_expired, frame_order, frame_hash, invalid_box и другие ошибки без раскрытия данных.

Изменение серверное, совместимо с текущим collector v3; новый архив для его применения не требуется. До проверки продолжительного реального просмотра оно не считается подтверждением стабильной работы на Hostrix.


## Реальный результат после серверного исправления

Трёхминутная проверка настоящего v3 на Hostrix: 362 различных кадра, 133 опроса API, 0 сетевых ошибок теста и 0 обнаруженных рестартов. После первых 15 секунд только 62 из 122 опросов (50.8%) видели последний кадр моложе 5 секунд; максимальный возраст достиг 11.329 с. Это подтверждает восстановление передачи, но **не плавное видео и не низкую задержку**. Число временных ID не является оценкой числа машин или устойчивости сопровождения.

В браузере найден дополнительный источник рывков: при stale-ответе очередь сбрасывалась и показывался последний кадр, затем свежий ответ мог заново проигрывать более раннюю часть окна. Исправление сохраняет временную отметку последнего показанного кадра. Задержанные ответы не могут отмотать изображение назад. При возрасте до 15 секунд реальные кадры продолжают воспроизводиться с явным статусом задержки и серыми рамками; при большей задержке остаётся один последний кадр. Новые координаты и промежуточные изображения не создаются.

Browser QA проверяет, что после ответа с более старыми captured_at показанное время не уменьшается. Производственная браузерная проверка отдельно измеряет фактическую частоту показанных кадров, паузы, возраст и наличие обратного хода, не приравнивая появление рамки к стабильной видеотрансляции.


Первая производственная проверка порядка кадров: 29 показанных кадров за 30.9 с (~0.94 fps), 0 переходов назад, максимальная пауза 4.55 с, максимальный возраст показанного кадра 6.162 с. Она выявила потерю кадров при underrun: часы воспроизведения продолжали идти при пустой очереди и считали пришедший пакет целиком опоздавшим. Следующая правка приостанавливает эту временную шкалу и начинает новый фактический пакет с небольшим буфером, сохраняя отметку последнего показанного captured_at. Это проверяется отдельным regression test; реального 25–30 fps такая правка не создаёт.


## Итоговая проверка воспроизведения

После восстановления временной шкалы при пустой очереди production browser probe показал 73 настоящих кадра примерно за 31.2 с = 2.337 fps, 0 кадров с обратным captured_at, максимальную паузу 2.714 с и возраст показанного кадра до 7.09 с. В браузере наблюдались реальные vehicle ID v3, overlay соответствовал изображениям, uncaught errors=0, collector online. 29 API-ответов были старше пяти секунд; это остаётся измеренной задержкой, а не скрывается как realtime. Возраст считается от collector_arrival и не включает неизвестную дополнительную задержку HLS/часов камеры. Прогоны до и после выполнялись в разное время, поэтому их нельзя считать контролируемым сравнением CPU/источника.

Финальный [CI](https://github.com/subrosa5/roadwatch/actions/runs/43630523096): success, 48 Node + 28 Python tests и E2E. Для непрерывного исходного HLS существует отдельный режим «Живое видео», фоновый анализ событий от него не зависит.
