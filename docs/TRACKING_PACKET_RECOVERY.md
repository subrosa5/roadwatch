# Восстановление доставки после задержки пакета

После запуска v3 API подтвердил работающий collector и реальные vehicle ID, но проверка длительного просмотра обнаружила паузы. Worker-логи содержали POST /tracking с HTTP 400. Сам код ответа не раскрывает конкретную причину остановки процесса на Hostrix; для неё нужен его свежий лог либо типизированная серверная диагностика.

Воспроизведён отдельный дефект протокола: пакет с кадром шестисекундной давности и свежим последним кадром целиком отклонялся из-за ограничения длительности пакета. Клиент мог рассматривать такое отклонение как постоянную ошибку и завершать процесс. Раньше regression test получал 400 вместо ожидаемого 200.

Теперь API сначала проверяет согласованность всех пар JPEG/annotation, роли, хеши и порядок кадров. Последний кадр по-прежнему обязан быть моложе пяти секунд. После этого старая часть пакета отбрасывается, а свежая принимается. В квоту входят только оставшиеся новые кадры. Протухший целиком пакет, неверный хеш или неверные рамки остаются отклонёнными.

Добавлены фиксированные коды диагностических сообщений tracking_ingest. В них нет текста запросов, изображений, ключей, подписанных URL или произвольного содержимого ошибок. Это позволит отличать frame_expired, frame_order, frame_hash, invalid_box и другие ошибки без раскрытия данных.

Изменение серверное, совместимо с текущим collector v3; новый архив для его применения не требуется. До проверки продолжительного реального просмотра оно не считается подтверждением стабильной работы на Hostrix.
